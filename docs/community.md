# Community

## Where conversations should happen

After the public repository is created, enable GitHub Discussions if there is enough maintainer capacity to moderate it. Suggested categories are:

- **General** for project-wide conversation
- **Ideas** for proposals that are not ready for an issue
- **Q&A** for development and usage questions
- **Show and Tell** for integrations built with synthetic or safely redacted examples

Discussions are a recommendation, not a currently enabled feature. Confirm category names and moderation contacts during repository setup.

Use issues for reproducible bugs and scoped feature work. Use pull requests for reviewable changes. Do not use any public channel to disclose vulnerabilities, credentials, private records, authentication state, or customer data; follow [SECURITY.md](../SECURITY.md).

## Participation

- Read the [Code of Conduct](../CODE_OF_CONDUCT.md).
- Search before opening a new topic.
- Explain the use case without pasting data you do not have permission to share.
- Keep adapter discussions within the [compliance boundary](compliance.md).
- Label assumptions and incomplete experiments clearly.
- Do not manufacture stars, downloads, issues, forks, or contributor activity.

## Maintainer practice

Maintainers should publish decisions in the relevant issue or discussion, close duplicates with a useful pointer, and avoid promising a release date before the work is scoped. Security and conduct reports need private channels before public community launch.
